# Jardamchy GO

## Jardamchy GO Web Test

Легкая веб-версия WhatsApp-бота для локального тестирования:

```bash
pip install -r requirements.txt
python src/web_test_app.py
```

После запуска откройте `http://127.0.0.1:5050`.

Основная логика тестового веб-чата находится в `src/web_test_app.py`. Файл не дублирует сценарии бота: он вызывает `src/main.py::handle_whatsapp`, а внешние интеграции WhatsApp, Telegram и PostgreSQL заменяет in-memory mock-слоем. Интерфейс находится в `src/web_test_static/index.html`.

`Jardamchy GO` — мультисервисная платформа для Шамалды-Сая: клиенты оформляют заявки через WhatsApp и web-menu, исполнители принимают их в Telegram, администраторы управляют системой через web-панель. Бэкенд работает на Flask + PostgreSQL и уже включает очереди, повторные отправки и фоновые cron-проверки для защиты от cold start и временных сбоев.

## Что актуально сейчас

Старые описания про Google Sheets, 6 сервисов и прежние сценарии больше не соответствуют реальному проекту. На текущий момент система:

- работает на PostgreSQL через `psycopg2` и `ThreadedConnectionPool`
- принимает входящие WhatsApp webhook-события через очередь `whatsapp_webhook_queue`
- отправляет заявки в Telegram-группы через очередь `telegram_group_outbox`
- поднимает фоновые cron-задачи каждые `30 секунд`
- обслуживает сразу три интерфейса: бот, админ-панель и web-menu
- поддерживает новые бизнес-флоу: `7 область такси`, `разнарабочий`, web-menu кафе, доставка своим курьером кафе

## Ключевые сценарии

### 1. Кафе и web-menu

- Клиент может заказать еду напрямую в WhatsApp или через публичное меню по адресу `/menu/`.
- `menu_panel/` показывает список кафе, категории, блюда, скидки и корзину.
- Web-menu создаёт запись в `web_orders`, генерирует код вида `W12345` и формирует ссылку в WhatsApp с полным текстом заказа.
- WhatsApp-бот умеет распознавать не только голый код, но и сообщение формата `Заказ с сайта ... Код: W65738`.
- После принятия заказа кафе указывает время готовности и выбирает один из вариантов доставки:
  - `Своим курьером`
  - `Курьером Жардамчы GO`
- Если кафе выбирает своего курьера, бот запрашивает номер телефона, отправляет его клиенту и не отдаёт заказ группе таксистов.

### 2. Магазин

- Клиент отправляет список продуктов и адрес.
- Система создаёт заказ с доставкой и дальше обрабатывает его через Telegram-сторону.

### 3. Такси, портер и желмаян

- Для маршрутов используется свободный текст.
- Бот извлекает `from/to`, показывает confirm и после подтверждения отправляет заказ в нужную Telegram-группу.

### 4. 7 область такси

Это уже не старый legacy-flow `направление -> дата -> места`, а отдельный современный сценарий.

- Первый экран спрашивает: `Адам же жүк?`
- Есть две WhatsApp-кнопки:
  - `oblast_type_person`
  - `oblast_type_cargo`
- Свободный текст на первом сообщении тоже принимается.
- Поддерживаются кейсы:
  - `Шамалды-Сайдан Ошко 2 адам`
  - `Шамалды-Сайдан Ошко телефон салыш керек`
  - `Ошто телефон алып берүү`
- Для `адам` комиссия считается как `20 сом * количество человек`.
- Для `жүк` комиссия фиксированная: `20 сом`.
- Итоговая комиссия записывается в `orders.price_total`.
- Если в грузовом сообщении известна только одна точка, бот не додумывает вторую, а отдельно спрашивает недостающий адрес.

### 5. Разнарабочий

- Бот умеет разбирать и комбинированные сообщения, например: сколько людей нужно и какая работа.
- Если описание есть, а количество нет, бот спрашивает только недостающий кусок.
- Если никто не принял заказ, он автоматически отменяется через `30 минут`.
- После автоотмены клиент получает выбор:
  - `Повторить`
  - `Отменить`

### 6. Мед эже, мастер, маалымдама, компьютерные услуги

- `Мед эже` работает как быстрый информационный/контактный сценарий.
- `Мастер кызматы` использует категории мастеров и справочник исполнителей.
- `Маалымдама` отдаёт справочник важных номеров.
- `Компьютердик жардам` сейчас является информационным блоком, а не полноценным заказным flow.

## Telegram-сторона

Telegram используется для исполнителей и групп услуг:

- регистрация водителей и исполнителей
- приём заказов из групп
- проверка баланса и автосписание комиссии
- inline-кнопки для принятия и завершения сценариев
- отдельный flow для кафе, включая выбор типа доставки

Группы и роли на стороне Telegram:

- `GROUP_CAFE_ID`
- `GROUP_SHOP_ID`
- `GROUP_TAXI_ID`
- `GROUP_PORTER_ID`
- `GROUP_ANT_ID`
- `GROUP_POPUTKA_ID`
- `GROUP_RAZNARABOCHI_ID`

Для `7 область такси` Telegram take-flow остался совместимым по callback и service key, но списывает комиссию уже из `order.price_total`, а не из жёсткой константы, если сумма была рассчитана динамически.

## Надёжность и анти-потери

Это один из главных блоков, которого не было в старой документации.

### Очередь входящих WhatsApp webhook

- Все входящие JSON webhook-данные сначала сохраняются в `whatsapp_webhook_queue`.
- Затем они обрабатываются worker-потоком и фоновым циклом.
- На старте приложения очередь дополнительно подбирается повторно.
- Это снижает риск потери сообщений при cold start или кратковременной ошибке приложения.

### Очередь исходящих Telegram-сообщений в группы

- Отправка в Telegram-группы идёт через `telegram_group_outbox`.
- Если Telegram недоступен или приложение стартует слишком медленно, сообщение не теряется, а повторяется позже.
- На старте приложения outbox тоже восстанавливается и дозапускается.

### Фоновые cron-задачи

Фоновые задачи запускаются каждые `30 секунд` и обрабатывают:

| Проверка | Значение |
| --- | --- |
| `CAFE_AUCTION_TIMEOUT` | `120` секунд |
| `PHARMACY_RESPONSE_TIMEOUT` | `300` секунд |
| `TAXI_RESPONSE_TIMEOUT` | `300` секунд |
| `RAZNARABOCHI_RESPONSE_TIMEOUT` | `1800` секунд |
| `TAXI_ACCEPTED_TIMEOUT` | `1800` секунд |
| `PENDING_ORDER_AUTO_CANCEL_TIMEOUT` | `1200` секунд |
| `IN_DELIVERY_AUTO_COMPLETE_TIMEOUT` | `1800` секунд |

## AI и обработка сообщений

Текущая AI-часть:

- NLU: `GPT-4.1-mini` через `src/nlu.py`
- Speech-to-text: основной путь через OpenAI audio transcription API с `gpt-4o-transcribe`
- для распознавания голосовых используется контекстный prompt с локальными названиями и типовыми словами

Важно:

- бот не опирается только на модель
- поверх модели построена детерминированная state machine
- для части сценариев есть service-specific парсеры и эвристики, например для `такси`, `разнарабочий` и `7 область такси`

## Админ-панель

Админка расположена в `admin_panel/` и доступна по `/admin/panel`.

Сейчас она покрывает:

- dashboard и агрегированную статистику
- заказы
- водителей и баланс
- кафе
- пользователей
- shoppers
- транзакции
- runtime settings
- рассылки в Telegram и WhatsApp

Отдельно меню кафе обслуживается через `menu_panel/` и backend-маршруты `/menu/api/*` и `/menu/api/admin/*`:

- кафе
- категории меню
- блюда
- скидки
- web-заказы

Недавнее исправление по админке: пополнение и списание баланса больше не падают из-за отсутствующего `loadShoppers` в `admin_panel/app.js`.

## Локальный запуск

### 1. Установка зависимостей

```bash
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
```

### 2. Настройка `.env`

Создайте `.env` и задайте хотя бы:

```env
DATABASE_URL=postgresql://user:pass@localhost/business_assistant
TELEGRAM_BOT_TOKEN=...
OPENAI_API_KEY=...
WHATSAPP_PROVIDER=cloud
WHATSAPP_TOKEN=...
WHATSAPP_PHONE_NUMBER_ID=...
WHATSAPP_VERIFY_TOKEN=...
```

### 3. Запуск

Для локальной разработки:

```bash
python src/app.py
```

Для production-подобного запуска:

```bash
gunicorn --chdir src -w 2 -b 0.0.0.0:$PORT app:app
```

## Legacy и важные замечания

- Аптечный модуль и часть связанной логики всё ещё существуют в коде и БД, но не входят в текущее клиентское главное меню.
- В проекте остаются legacy-константы и совместимые имена вроде `POPUTKA_*`, хотя реальный клиентский flow уже называется `7 область такси`.
- Google Sheets упоминаются только как legacy/backup-контекст. Основная рабочая БД — PostgreSQL.
